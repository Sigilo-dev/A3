# E1-D1 — transición y recuperación del journal

Estado: contrato de implementación. Base `f8d85af` (E1-C2), contratos E0-A, evidencia E0-C1 y especificación maestra §§7–8 y 28. El journal operativo vive en `.a3/local/transactions/`, excluido de Git y de los datos portables. Solo guarda IDs, rutas relativas, hashes, revisiones, identidades locales de archivo, copias de bytes separadas y avance; nunca prompts, credenciales ni contenido dentro de eventos.

## Transiciones

| Estado | Efecto y evidencia durable | Interrupción y decisión al abrir |
|---|---|---|
| Preparar | Crear carpeta exclusiva por `operationId`; escribir `intent.json` con versión/protocolo, proyecto, conjunto de rutas, read set, hashes/revisiones y nombres de artefactos. Enlazarla al primer evento hash-chain. | Sin intención y registro íntegros no se adivina la operación: se aísla la carpeta y el proyecto queda en solo lectura con diagnóstico. |
| Respaldar | Guardar `.before` independiente para cada destino existente, `.staged` independiente para cada contenido propuesto y `.candidate` instalable. Sincronizar cada archivo y registrar `staged(index)`; comprobar sus hashes antes de aplicar. | Si aún no empezó la aplicación y el read set sigue igual, cerrar como rollback sin tocar los destinos; conservar lo que haya de temporales. |
| Aplicar | Registrar intención de separar/instalar antes de cada efecto. Separar el nombre previo en `.detached`; crear el destino únicamente con hardlink exclusivo del candidato. Cada archivo se registra por separado. | Nunca se declara atómica la operación lógica. Un lector puede ver el intervalo sin nombre y un estado parcial. |
| Confirmar | Verificar todos los destinos contra `afterHash`, artefactos recuperables y dependencias; sincronizar `verified` y `committed`. El recibo tiene `atomic: false`. | Tras reinicio se confirma si todos los destinos aún coinciden en bytes e identidad con el candidato (o están ausentes según una eliminación) y el resto del read set no cambió. Se completa el marcador sin volver a aplicar efectos. |
| Revertir | Solo cuando no se puede confirmar y cada destino está en el estado anterior, aplicado o en el intervalo registrado; el resto del read set conserva hash e identidad. Mover primero cualquier salida aplicada a un nombre recuperable exclusivo y restaurar desde una copia `.before` mediante un candidato independiente. Verificar el estado anterior y marcar `rolled-back`. | Cada paso es repetible: los nombres de recuperación son deterministas y exclusivos; ante reinicio se inspeccionan bytes/identidades antes de continuar. Los backups y las salidas preservadas permanecen en el journal. |
| Conflicto | Si una ruta contiene una tercera versión, el read set externo cambió, un artefacto necesario no coincide o la evidencia no permite decidir, conservar destino y artefactos, registrar `recovery-conflict` cuando el journal permita y bloquear escrituras. | No se restaura ni reemplaza ningún destino. La interfaz recibe diagnóstico/rutas para revisión. La resolución manual será una operación recuperable posterior. |

Una carpeta con JSON/UTF-8 inválido, hash-chain roto, versión/protocolo desconocido o registro truncado se mueve completa a `transactions/quarantine/` bajo un nombre derivado de su nombre original. Se conserva íntegra y se diagnostica. La cuarentena bloquea la escritura automática: no se interpreta como una transacción resuelta.

La decisión es global para la operación: estado propuesto completo confirma; estado mixto compuesto solo por versiones anteriores/propuestas/intermedias revierte; cualquier estado ajeno produce conflicto sin mutaciones de recuperación. La repetición del arranque observa los mismos artefactos y termina en el mismo marcador, sin duplicar aplicaciones.

La sincronización de archivos y el orden del journal solo respaldan recuperación tras interrupción del proceso observada. E0-C1 no pudo sincronizar metadatos de directorio y no ensayó corte de energía; no se promete tolerancia a pérdida eléctrica, persistencia física, atomicidad de varios archivos, protección frente a procesos locales maliciosos ni recuperación automática de un journal aislado.

## Implementación y evidencia

`@a3/project-store` usa `.before`, `.staged`, `.candidate` y `.detached` del protocolo E1-C2. El rollback crea `.recovery-applied` para retener la salida ya instalada y `.recovery-restore` como copia independiente del backup antes de restaurar. Ambas rutas son deterministas por índice de entrada. El registro agrega `recovery-start` con decisión fija, `recovery-progress` por entrada y un cierre `recovery-committed`, `recovery-rolled-back` o `recovery-conflict`. Un cierre completo no repite efectos al volver a abrir; si el proceso termina a mitad del rollback, hash/identidad y artefactos permiten reanudarlo. Los journals C2 anteriores a actor/revisiones siguen compatibles.

La prueba Windows 10 x64, Node 24.13.1/npm 11.10.0, en carpeta temporal NTFS termina procesos reales con `process.exit(86)` tras intención, staging, separación, antes/después de instalar, antes de confirmar y después del commit. Un Resource cambia descriptor y fuente en un lote de dos archivos. Antes de que todos los destinos coincidan se restaura el estado previo; cuando todo coincide se completa el marcador. También se interrumpe y repite rollback, se interrumpe confirmación, se confirma un borrado aplicado, se conserva una edición y una eliminación externas junto a `.before`/`.staged`, y se termina el proceso antes/después de aislar un journal truncado. Se verifica la segunda apertura sin cambios duplicados y que los registros truncados acaban en cuarentena.

La suite completa pasó con 34 pruebas E0, 44 de dominio y 74 de store (**152** en total); `npm run typecheck` y `npm run build` también pasaron. No se añaden dependencias ni se cambian schemas/fixtures E0. Los casos usan terminación de proceso, no corte de energía. A3-030 recibe evidencia parcial para repetir recovery de un `operationId` local; no se integra la reanudación de app-server. A3-038 tiene backup y rollback verificables, pero sigue pendiente el historial local visible, snapshots con retención, restauración coordinada con Git y su UI. A3-046 cubre fallos de proceso; A3-047 detecta y conserva edición/eliminación externas sin UI diff/merge; A3-048 mantiene lectura segura de versión desconocida, sin ejecutar migraciones.
