# E1-E2: resolución de rutas y montajes locales en Windows

Relaciona A3-002, A3-003 y A3-024. El archivo de especificación maestra citado por el prompt no está presente en el checkout ni en `origin/codex/e1-base`; este corte sigue el contrato E0-A de `Resource.mounted-file`, el broker E1-E1 y la evidencia C2.

Cada `mounted-file` compartido guarda únicamente el `mountId` UUID y una ruta relativa portable con `/`. El path absoluto de la raíz y el permiso máximo local viven fuera del proyecto en el estado del host, ligados al hash de la ruta canónica del proyecto y a su UUID. Un proyecto importado o clonado solo solicita el montaje. Requiere que la persona seleccione una carpeta local y la apruebe de nuevo; `policies.json` no puede asignar una raíz.

La aprobación persiste la raíz canónica, identidad del directorio y permiso `read-only` o `read-write`. En Windows se aceptan raíces locales con letra de unidad; se rechazan UNC, rutas de dispositivo y raíces que ya no sean carpetas. Cada operación vuelve a comprobar existencia, identidad y canonicalización. Si desaparece, se mueve o se reemplaza la raíz, el servicio entrega `mount-root-missing` o `mount-root-changed`; el descriptor del proyecto permanece intacto para volver a seleccionar la raíz y recuperar la referencia.

`readMountedResource` y `ProjectService.openResource(id)` exigen las dos concesiones actuales: `mount.read` del broker del proyecto y la aprobación local del mount ID. El lector rechaza rutas absolutas, `..`, segmentos ambiguos y enlaces; valida cada segmento con `lstat` y `realpath`, abre un handle, compara su identidad con la ruta validada, revalida el árbol antes de leer y vuelve a comprobarlo al terminar. Lee bytes acotados por handle, detecta crecimiento/cambio durante lectura y devuelve solo ruta relativa, hash y bytes. No enumera recursivamente ni indexa una carpeta completa todavía.

`previewMountAction` muestra destino, conflictos y capacidades para tres acciones distintas. `reference` crea un descriptor `mounted-file` sin tocar bytes externos. `copy` lee la fuente por el broker y crea el descriptor `project-file` y la copia mediante el writer/journal del proyecto. `move` se previsualiza como acción separada, pero `prepareMountAction` la rechaza con `mount.write`: borrar una fuente externa por ruta conserva una carrera con junctions, y Node no aporta aquí una operación de borrado por handle que cierre ese caso. Incluso una concesión local `read-write` o una solicitud compartida no activa `mount.write`.

Un recurso remoto URL sigue sin lector y requiere una futura frontera de red aprobada. Las guardas de rutas solo median operaciones del host A3; no contienen un proceso del mismo usuario que abra archivos directamente. E0-C2 ya demostró ese límite para procesos arbitrarios, que permanecen deshabilitados. Las pruebas usan raíces temporales sintéticas y cubren traversal, lectura, clonación, permisos, conflictos de destino, copia/referencia, raíz movida/reemplazada, junction y sustitución entre validación y apertura.

Comprobación observada en Windows: `node --test packages/project-store/test/mounts.test.mjs` pasa 10 casos. `npm test` pasa 34 contratos E0 + 44 dominio + 96 store = 174 pruebas; `npm run typecheck` y `git diff --check` también pasan. El build del workspace `@a3/project-store` se ejecuta dentro de la suite.
