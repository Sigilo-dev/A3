# ADR 0021 · autorización oficial ChatGPT en el host

Estado: ciclo OAuth en host implementado en E5-B1/B2; autorización real e inferencia pendientes. Fecha: 2026-10-17. Base: E5-A1 `637f616`, especificación §§20.1–20.3/21.4 y evidencia [E0-B2](../e0/compatibility/codex-app-server.md)/[E0-C2](../e0/compatibility/windows-process-isolation.md).

## Decisión

Usar el cliente público OSS/local documentado por OpenAI: registro dinámico `dynamic_agent_client`, nombre A3, host ID estable y autorización en el navegador del sistema. No se usa un client secret, clave API del desarrollador, cookies de ChatGPT, login del CLI personal ni fallback de pago. La disponibilidad documentada para usuarios elegibles no acredita la elegibilidad de una cuenta concreta; esta entrega no hace una consulta de inferencia. [Registro oficial](https://developers.openai.com/siwc/token-sharing-open-source/sign-in).

`CodexAuthorization` administra intentos/cuentas, callback loopback y transporte de identidad. El constructor recibe bóveda, apertura del navegador y transporte; solo el host los configura. `SystemCredentialVault` adapta `safeStorage` de Electron 44.7.2. No se conecta el dominio o store de proyecto a estos objetos. Las consultas del futuro app-server usarán otro adaptador versionado y deberán comprobar las capacidades del proyecto y el permiso efectivo en cada operación. Este bloque no habilita `network.access` ni procesos arbitrarios de E0-C2.

La autorización escucha primero en `127.0.0.1`, puerto efímero y `/auth/callback`; solo varía el puerto entre intentos. Guarda en memoria el redirect exacto, state/nonce aleatorios de 256 bits y PKCE S256. Verifica método, Host, origen, dirección remota, ruta, parámetros duplicados y state antes de usar código/error. Un intento es consumible una vez, cancelable y expira a los cinco minutos. El intercambio reutiliza el redirect exacto y el client ID emitido; un registro existente no acepta otro ID/subject. `invalid_grant` conserva el ID emitido en memoria para reintentar sin repetir registro en esa ejecución.

Discovery debe declarar el issuer esperado y endpoints authorize/token exactos. JWKS/revocación deben ser HTTPS del mismo origen oficial sin credenciales, query ni fragmento. El transporte no sigue redirecciones, no utiliza cookies, limita cada petición a doce segundos y cada JSON a 256 KiB. Ninguna URL configurable llega por IPC. ID token: firma RS256 con JWKS descubierto, issuer, audience del client emitido, exp/iat, nonce inicial y azp cuando corresponda. No se descarga una clave desde parámetros del JWT.

`jose` **6.2.12**, MIT, se fija en manifest/lock para validar JOSE/OIDC; no tiene dependencias de runtime. Se inspeccionaron `node_modules/jose/package.json` y `LICENSE.md` y [su fuente oficial](https://github.com/panva/jose). No se actualizan otras dependencias. El bundler lo usa en main; no se importa en preload/renderer. El inventario/avisos del instalador final siguen pendientes de E7.

El permiso se determina por los scopes concedidos en la respuesta del token, nunca por el callback o la identidad sola. Se exigen `openid` y un ID token válido; para permiso del plan se exigen `resource.invoke` y `chatgpt.tokens.use.direct`, además de access token vigente. E5-B2 persiste condiciones host-only de cuenta para elegibilidad, cuota e indisponibilidad; la UI muestra estas condiciones, token vencido, identidad sin permiso y concesión aún no probada. Una señal `completed` del futuro proveedor puede marcar `inferenceVerified`; el adapter falso la prueba, pero no hay un app-server conectado que pueda hacerlo en uso real. Añadir/seleccionar otra cuenta no mezcla registros. Cada etiqueta local opaca es estable; no se envían claims o email al renderer.

## Persistencia y desconexión

Se guarda un único envelope versionado cifrado en `userData/codex-authorization/credentials.bin`, fuera del proyecto: host ID, registro por client/subject verificado, selección, ID/access/refresh tokens, scopes y expiración. Un temporal exclusivo del mismo directorio recibe solamente ciphertext, se sincroniza y reemplaza el archivo. No se promete durabilidad ante corte eléctrico. El perfil usa el bloqueo de instancia única del host; las operaciones OAuth se serializan en el controlador. Cancelar durante una escritura restaura el envelope anterior antes de admitir otro comando. El cierre normal aborta y espera las operaciones en curso.

Solo Windows con `safeStorage.isEncryptionAvailable()` queda habilitado: DPAPI es la integración comprobada. La falta de protección o un archivo que no pueda descifrarse/validarse falla cerrada y conserva el original; no crea un registro vacío para sobrescribirlo. Linux, incluido `basic_text`, queda deshabilitado hasta validar su backend. El `.gitignore` excluye también carpetas `codex-authorization` como defensa adicional.

DPAPI protege los bytes con el contexto del usuario de Windows. No confina otros procesos que ya tengan los mismos privilegios del usuario, ni protege contra un host comprometido; los tokens necesariamente existen en memoria del proceso principal. No se incluyen en respuestas IPC, URLs del shell, proyecto, journal, índice, snapshots, portapapeles ni logs. El ID token retenido puede viajar como `id_token_hint` exclusivamente al authorize oficial en el navegador del sistema, como indica el protocolo; A3 no registra esa URL. [Seguridad de safeStorage](https://www.electronjs.org/docs/latest/api/safe-storage).

Renovar es una acción explícita del host: conserva client/subject, omite scope en refresh y sustituye juntos access/refresh/expiración/scopes, conservando ID token si no se retorna otro. Un ID token nuevo debe validar la misma identidad. Un error terminal de refresh elimina los tokens inutilizables; una indisponibilidad temporal los conserva. Una rotación aceptada por el servidor pero interrumpida antes de persistir puede exigir reautorizar; no se promete recuperar una credencial remota perdida.

Desconectar intenta revocar el refresh token mediante el endpoint descubierto y elimina los tokens locales conservando registro/host para reautorizar. Si no se confirma revocación, se indica desconexión local y se pide revocar también en Ajustes de ChatGPT; no se anuncia éxito remoto. No se consulta automáticamente el estado remoto al restaurar y no hay notificación push de revocación. [Sesiones oficiales](https://developers.openai.com/siwc/token-sharing-open-source/profiles-and-sessions).

## Límites de la UI y aceptación

El único canal nuevo es `a3.codex:authorization`: state/connect/select/cancel/refresh/disconnect/open-usage, con payload estricto y guards de WebContents/frame/URL del shell. No acepta tokens, endpoints, código OAuth, scripts, rutas o claves. La respuesta contiene estados, diagnóstico fijo, IDs/etiquetas de cuentas y booleanos; los errores del proveedor se reducen a códigos permitidos, sin copiar cuerpos o URLs. La sesión web manual conserva su partición y cookies; cerrar una sesión no desconecta la otra. El enlace de uso abre una URL fija de ChatGPT, sin enviar datos de cuenta al sitio.

La prueba Windows de E5-B1 usa credenciales sintéticas, DPAPI real y dos procesos sucesivos. Las pruebas E5-B2 usan provider adapter falso para mapear condiciones y confirmar retención/redacción; no autorizan una cuenta, comprueban región/plan real, ejecutan app-server/turno, consumen créditos ni prueban revocación en producción. A3-028 sigue parcial; A3-029 tiene pruebas sintéticas de expiración, elegibilidad, denegación, cuota y disponibilidad, no acceso real a modelos o límites de inferencia. A3-030 y el aislamiento de procesos continúan fuera de este bloque. Véase [E5-B2](../e5/authorization-lifecycle.md).
