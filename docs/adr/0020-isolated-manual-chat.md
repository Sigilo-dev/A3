# ADR 0020 · chat web manual aislado

Fecha: 2026-10-17. Base: E4-E1 `14a7083`, A3 §19.1–19.3, [spike E0-B1](../e0/compatibility/chat-web.md) y [límites E0-C2](../e0/compatibility/windows-process-isolation.md). Entrega E5-A1, sin nuevas dependencias ni cambios del formato portable.

## Decisión

El host crea `WebContentsView` como hija de `BrowserWindow.contentView`. La UI local conserva pestañas, dirección/origen y controles; una región rectangular del renderer delimita dónde presentar la vista nativa. La vista se retira al salir de Chat web, abrir actividad/modal local o recargar el shell. Cambiar tamaño recalcula los límites. Ocultar conserva el documento web vivo; cerrar requiere aviso porque no se inspecciona su DOM para adivinar texto pendiente.

La vista remota no usa preload: `nodeIntegration`, Node en workers/subframes y `webviewTag` están desactivados; `contextIsolation`, `sandbox`, `webSecurity` y `safeDialogs` activados. No se cambia la CSP del shell, el user agent, TLS ni la verificación de certificados. No se inyecta JavaScript, se extraen chats, se leen cookies para autenticar agentes ni se seleccionan archivos del proyecto. El popup original siempre se deniega; una aprobación puede crear otra vista con los mismos límites, sin `window.opener` privilegiado.

`a3.manual-chat:command` contiene controles tipados de navegación, región, ciclo de vida y copia manual de texto. Exige el WebContents y frame principal del shell, URL local esperada, forma estricta del payload y sesión vigente del proyecto (o `null` sin proyecto). No expone evaluate, transporte IPC crudo, comandos A3, rutas, lectura del portapapeles ni envío al proveedor. Copiar texto desde el compilador admite hasta 1 MiB UTF-8 y solo escribe el portapapeles por una acción explícita; no pega ni inicia un turno.

La cuenta web inicial usa la partición `persist:a3-manual-chatgpt-v1`, distinta de `persist:a3-shell`. Cookies/almacenamiento quedan bajo el perfil de la aplicación, fuera de datos portables. Es una partición del proveedor y su flujo de autenticación: las cookies de cuenta pueden sobrevivir a cambiar de proyecto, pero las pestañas no se convierten en memoria/contexto A3. Cambiar proyecto confirma el cierre de pestañas y descargas pendientes; IDs de la sesión anterior dejan de ser válidos. OAuth/app-server es otro flujo y no está implementado por esta decisión. Futuras extensiones deben registrar proveedor/partición y política; no reciben acceso al constructor ni al puente del host.

Navegación y apertura externa aceptan HTTPS público sin credenciales, con control de protocolos, nombres locales e IP literales; recursos HTTPS/WSS y data/blob de subrecursos mantienen las reglas del navegador. Esto no es un firewall ni una protección de DNS del SO. `file:`, `a3:`, HTTP, esquemas ejecutables y navegación de frames data/blob quedan denegados. Un error de carga muestra la alternativa externa, que requiere confirmación de origen. No se evita una restricción de login del proveedor.

Permisos: cámara/micrófono solo para un frame principal visible y origen coincidente, con aprobación nativa, concesión de sesión por origen y revocación con recarga. Ambos handlers Electron de permisos están configurados. FileSystem, dispositivos, captura de pantalla, geolocalización, notificaciones, portapapeles web programático y permisos desconocidos se deniegan. Los permisos de este navegador manual no conceden capacidades al broker de archivos/procesos del proyecto.

Una descarga HTTPS exige gesto manual, pestaña visible y `DownloadItem.getInitiatorOrigin()` coincidente con su frame principal. El diálogo nativo síncrono dentro de `will-download` exige origen/destino antes de autorizar `setSavePath`, con confirmación para reemplazar un archivo. No se fija un destino desde la web ni se abre/ejecuta el resultado. Añadirlo como Resource requiere otro flujo explícito del explorador. Descargas blob/no admitidas quedan bloqueadas con diagnóstico. E0-C2 sigue sin acreditar aislamiento de comandos arbitrarios del SO; E5-A1 no ejecuta esos comandos ni altera ese bloqueo.

## Consecuencias y evidencia

Se mantienen hasta ocho vistas por proceso. Las inactivas conservan formularios; no se promete suspensión automática, recuperación de borradores web tras reinicio o compatibilidad de todos los OAuth. Cerrar sesión cierra las vistas y elimina datos locales de la partición; no es revocación global de cuenta ni logout del navegador externo. Si la limpieza falla, no se anuncia éxito y se bloquean nuevas vistas hasta reintentar.

APIs contrastadas con `electron.d.ts` instalado de **Electron 44.7.2** y documentación oficial: [WebContentsView](https://www.electronjs.org/docs/latest/api/web-contents-view), [webContents y navigationHistory](https://www.electronjs.org/docs/latest/api/web-contents), [Session, permisos y clearData](https://www.electronjs.org/docs/latest/api/session), [DownloadItem](https://www.electronjs.org/docs/latest/api/download-item), [guía de seguridad](https://www.electronjs.org/docs/latest/tutorial/security). No se actualiza Electron por esta entrega. La licencia/avisos de Electron siguen los ya aceptados en E0/E1; no se añade motor, SDK de IA ni biblioteca nueva.

La prueba de integración sustituye HTTPS solo en una partición temporal por fixtures controlados; no altera validadores de producción ni usa cuentas reales. Flags, procesos separados, probes de archivos/protocolo/IPC, permisos por origen, navegación, cierre, cookies, descargas y fallback se ejercitan con el Electron real.
