# E0-C2 — permisos efectivos y aislamiento de procesos en Windows

Consulta de documentación: 2026-10-14. Se leyeron la especificación maestra A3 1.0.0, §§8, 20–21, 24 y 30, los contratos E0-A y `windows-storage-recovery.md` de E0-C1. Esta prueba estudia guardas de rutas en un arnés y el token heredado por un proceso Node normal. No implementa el broker de permisos de A3.

## Resultado y entorno

El resultado es **parcial para las guardas lógicas y negativo para el aislamiento de procesos**. Las comprobaciones del arnés permitieron leer/escribir dentro de una raíz sintética, y rechazaron una ruta relativa que sale de ella y un junction que apunta a una carpeta hermana. Un `node:child_process.spawn` estándar sí leyó y escribió archivos sintéticos fuera de esa raíz, tanto por `..` como por junction, incluso después de que el arnés revocara su concesión lógica. No se concedió un token restringido ni se lanzó un AppContainer. Por tanto, esta ejecución demuestra que esas guardas del proceso A3 no contendrían por sí solas un comando secundario.

Entorno observado: Windows 10 Pro 10.0.19045 (22H2), Node.js v24.13.1, npm 11.10.0, en el volumen temporal local. La documentación Node v24 consultada el 2026-10-14 era v24.22.0; no es el binario probado. No se ejecutó Electron. El checkout no contiene un lanzador nativo de AppContainer, token restringido ni Job Object. `WindowsSandbox.exe` no se resolvió desde PATH. Consultar la característica opcional `Containers-DisposableClientVM` falló con “The requested operation requires elevation”; no se elevó el proceso ni se infiere de ese error que Windows carezca de la característica. El aislamiento Win32 empaquetado que documenta Microsoft requiere Windows 11 24H2 o posterior, así que no está disponible en el Windows 10 medido.

## Reproducción y alcance del arnés

Desde la raíz del repositorio:

```powershell
npm test --prefix experiments/e0/windows-isolation
```

Resultado observado: exit code 0, 6 casos, 0 fallidos. El runner crea un directorio único `a3-e0-c2-*` en `%TEMP%`, comprueba su prefijo y ubicación antes de limpiarlo en `finally`, y genera ahí el árbol `granted/` y `ungranted/`. El segundo contiene un marcador y destinos de escritura sintéticos. El proceso hijo verifica el marcador y limita sus rutas calculadas al mismo directorio temporal. No se accede a documentos, datos personales ni archivos del repositorio desde el hijo. La última ejecución terminó el hijo y registró `tempDataCleaned: true`.

Las funciones `hostRead`/`hostWrite` representan una política lógica de prueba: consultan capacidades y resuelven ruta léxica y `realpath` antes de acceder. Este preflight muestra el caso esperado, pero no es un control del kernel y mantiene una carrera entre comprobar y abrir/reemplazar (TOCTOU). El arnés no es una implementación para producción, no prueba todas las formas de reparse point y no atribuye sus resultados al sandbox de Codex.

## Qué aplica realmente cada mecanismo

| Límite | Mecanismo | Evidencia y alcance real | Límite / decisión E0 |
|---|---|---|---|
| Permisos lógicos de herramienta | El host valida capacidad, raíz, revisión y acción en cada comando A3. | El arnés acepta dentro y rechaza `..`, junction y capacidad revocada. Es coherente con §21.3. | Solo controla llamadas que pasan por el host. No limita un hijo que abre archivos directamente; el preflight de rutas también puede tener TOCTOU. Mantenerlo como primera barrera y usar APIs de sistema para límites de procesos. |
| Lectura/escritura del proceso | ACL/DACL y token de Windows. Un proceso normal usa el contexto de seguridad del usuario que lo creó. | El hijo accedió a la carpeta sintética no concedida. El entorno (variables, cwd, handles stdio) no cambió su identidad. | ACL de usuario no sirve para separar dos procesos del mismo usuario si ambos reciben los mismos permisos. Un broker nativo tendría que lanzar con un token realmente limitado y conceder ACL solo a los recursos necesarios. |
| Token restringido | `CreateRestrictedToken` reduce privilegios/SID habilitados y añade SID restrictivos; el acceso a un objeto debe pasar tanto la comprobación normal como la restrictiva. Se puede crear el proceso con una API que acepte ese token. | Mecanismo documentado por Windows; no se creó token ni se cambió ACL en la máquina. | Es candidato para un launcher nativo, con pruebas de handles, descendientes, reparse points y acceso a cada carpeta. No afirmamos que sea un sandbox configurado en A3. |
| Contención de archivos/red/procesos | AppContainer (o LPAC) y SID/capacidades del paquete con DACL explícitas. AppContainer puede aislar recursos de sistema, archivos y red; se pueden conceder archivos concretos y la capacidad de red correspondiente. | Capacidad documentada por Microsoft para Windows 8+ y el proceso de creación del token. No se lanzó AppContainer. | Candidato para ejecutar comandos en una carpeta de staging concedida y sin capacidad de red por defecto. Requiere launcher nativo, ACLs y tests de escape; no es una propiedad automática de Electron, Node ni de una ventana. LPAC es más restrictivo, pero puede romper accesos de runtime y requiere declarar capacidades. |
| Agrupar/detener procesos | Job Object. Puede agrupar procesos para límites de recursos y terminación; los hijos se incorporan por defecto salvo opciones de breakaway. | Documentado, no probado. | Complemento para terminar proceso y descendientes al revocar/detener. Un Job Object no aplica ACL de archivos ni política de red; probar configuración de breakaway y pertenencia antes de prometer cierre del árbol. |
| Handles heredados | `CreateProcess` y `STARTUPINFOEX`/lista de handles permiten elegir qué handles heredar; `bInheritHandles = FALSE` evita herencia general. | El arnés pasó solo stdin/stdout/stderr. No abrió handles de archivos del usuario. | Útil para reducir autoridad accidental del hijo, pero no cambia token ni acceso discrecional al que el mismo usuario ya tiene acceso. |
| Staging y promoción | Copia temporal, cambios revisables, validación, hash/revisión y aplicación transaccional por el servicio A3. | E0-C1 probó de forma sintética recuperación de archivos; este spike no aplica lotes ni transacciones. | Staging ordena el flujo, pero una carpeta corriente bajo el mismo usuario no aísla un comando arbitrario. Ejecutar el hijo dentro de una frontera OS real; promover solo cambios revisados con `apply_changes` y la revisión/hash vigentes. Si no hay aislamiento, deshabilitar el comando. |
| Red saliente | AppContainer sin capacidad de red, o política de firewall/aislamiento OS diseñada para el ejecutable y probada. | Documentación indica que AppContainer sin capacidad de red no accede a la red; no se hizo una prueba local de red. | No anunciar red bloqueada por el mero hecho de ocultar herramientas o vaciar variables. Hasta tener lanzamiento y prueba del SO, negar red al proceso arbitrario. Las consultas de proveedor en Consultar pertenecen al adaptador autorizado, no a comandos arbitrarios. |

Microsoft indica que `CreateRestrictedToken` necesita las comprobaciones de DACL correspondientes y que AppContainer usa SID separados, ACL y capacidades. La documentación de Job Objects describe agrupación y ciclo de vida, no permisos sobre recursos. Node documenta `spawn` como creación de proceso con `cwd`, `env` y opciones de stdio; esas opciones no crean un token de Windows nuevo.

## Matriz de perfiles A3

Las decisiones de esta tabla aplican el contrato aprobado §§21.1–21.3: permisos del proyecto son solicitudes, concesiones efectivas son locales y capacidades independientes. “Evidencia” se refiere al ensayo sintético arriba, no a una implementación del producto.

| Perfil / capacidad | Mecanismo requerido | Evidencia | Límite | Decisión para E0 |
|---|---|---|---|---|
| Consultar — lectura | Herramienta del host, raíz autorizada y resolución real de rutas; AppContainer si un proceso externo debe leer. | Lectura positiva interna; salida por `..`/junction rechazada por host. | Un proceso con token normal alcanza otras rutas del usuario. | Lectura solo por host; proceso arbitrario deshabilitado. |
| Consultar — escritura | Capability check del host deniega edición. | La prueba negó lectura sin capability; el control de escritura usa el mismo gate. No hubo montaje/producto real. | El hijo normal puede escribir fuera del alcance lógico. | Escritura directa y procesos denegados. |
| Consultar — procesos | Política deniega; no se pide aprobación por comando en este perfil. | Rama `processGate` simulada sin spawn. | No es un broker de producción. | Deshabilitados. |
| Consultar — red | Adaptador de proveedor con capacidad separada; procesos sin red. | No se generó tráfico ni se probó firewall. | No se garantiza una red solo de proveedor para un hijo con mismo token. | No permitir red en procesos; proveedor usa su propio adaptador explícito. |
| Proponer — lectura | Herramientas del host sobre raíces concedidas. | Mismo caso lógico de host. | No confinar child process por policy. | Lectura mediada por host. |
| Proponer — escritura | Staging/diff; aprobación explícita; aplicación por comando A3 con revisión/hash. | No se aplicaron cambios; E0-C1 probó un harness transaccional sintético. | Una aprobación no reduce el token del proceso. Staging sin OS sandbox no protege archivos vecinos. | Permitir propuesta y `apply_changes` validado; comando bruto solo dentro de AppContainer/token restringido. Sin launcher disponible, deshabilitar ejecución. |
| Proponer — procesos | Aprobación por invocación más sandbox OS y alcance visible; broker debe limitar árbol/handles. | Se simuló fallo cerrado si isolation=false; no se probó un sandbox real. | Un diálogo de aprobación no confina el proceso tras iniciarse. | Aprobación sola no basta; deshabilitar si el aislamiento no está disponible. |
| Proponer — red | Concesión explícita más capability/política OS en proceso aislado. | No probada. | No se puede distinguir o limitar red arbitraria de forma efectiva en la ejecución probada. | Deshabilitada para comandos hasta implementar y probar el límite. |
| Trabajar — lectura | Herramientas A3 dentro de raíces locales otorgadas; proceso con aislamiento OS si ejecuta binarios. | Guardia lógica positiva y prueba de bypass por hijo. | Reglas del proyecto no restringen el token de proceso. | Mantener operaciones de dominio por el servicio; comandos solo aislados. |
| Trabajar — escritura | Escritura directa mediada por servicio dentro del ámbito, con historial/transacción; promoción de salidas de hijo por diff/hash/revisión. | E0-C1 comprobó un protocolo de recuperación sintético, no servicio A3. | A3 aún no posee un writer/ACL/launcher ejecutable. | Cambios de dominio por herramientas; salidas arbitrarias en staging aislado, validadas antes de promover. Sin aislamiento, capacidad de proceso deshabilitada. |
| Trabajar — procesos | Reglas explícitas de proyecto más token/ACL/AppContainer y Job Object para proceso/descendientes. | Child spawn estándar probó que no hay aislamiento implícito; no se probaron token ni Job. | Un proceso hijo de Node no es un sandbox; detener solo el padre puede dejar descendientes. | No habilitar comandos arbitrarios hasta que el launcher pase la matriz de pruebas. |
| Trabajar — red | Concesión explícita independiente; AppContainer capability o política OS comprobada. | No probada, cero conexiones realizadas. | Sin aislamiento, mismo token puede abrir sockets y tocar red con permisos del usuario. | Deshabilitada en comandos por defecto hasta prueba OS; no elevar privilegios para habilitarla. |

El campo `network` de `.a3/policies.json` y una confirmación de usuario son solicitudes de política, no controles del sistema. Si el aislamiento no está presente o falla al arrancar, el error debe ser visible (`PERMISSION_DENIED`/capacidad no disponible) y el proceso no debe iniciarse. Para cambios de dominio, la alternativa segura disponible en el contrato es preparar una propuesta y aplicar solo el lote validado con aprobación/revisión. Para una herramienta externa, el staging es seguro únicamente si el proceso corre bajo una frontera OS con acceso limitado; una carpeta temporal normal no basta.

## A3 y decisiones abiertas

| Requisito | Evidencia / relación con la especificación | Estado |
|---|---|---|
| A3-024 montajes | El arnés valida escape relativo y junction para las funciones del host. El hijo evita esas guardas y alcanza la carpeta hermana. No hubo mount real de A3. | Parcial; falta abrir el recurso montado desde A3 y asegurar el acceso al nivel del OS para procesos externos. |
| A3-031 perfiles | Tres rutas de política y “no spawn si isolation=false” se verificaron como aserciones del arnés. La prueba de child demuestra por qué permisos lógicos no bastan para comandos. | Parcial; falta integrar broker, grants locales y perfiles de producto. |
| A3-032 autoridad local | Un archivo de solicitud sintético pide `*`/proceso/red; la concesión local de test sigue limitada. | Simulación comprobada; falta intentar edición/importación en el broker real de A3. |
| A3-033 herramientas | No se llamó a `validate_changes`/`apply_changes`, no se probaron revisiones obsoletas ni conflictos. E0-A requiere volver a comprobar revisión/hash al aplicar; E0-C1 cubre otro harness de almacenamiento. | No probado en E0-C2; debe permanecer dentro de tools/servicio A3, no delegarse a escritura cruda del hijo. |
| A3-043 extensiones | El contrato E0-A mantiene los paquetes declarativos inertes y prohíbe ejecución automática al abrir. No se cargó una extensión programada. | Aislamiento, permisos y revocación de plugin quedan sin probar; mismo requerimiento de launcher/OS que para procesos. |

Decisiones para ADR antes de ejecutar comandos o plugins: escoger entre AppContainer/LPAC y token restringido según compatibilidad de Electron/binarios; definir ACL exacta para staging y cómo rechazar reparse points; controlar handles heredados, procesos descendientes y breakaway; especificar terminación/revocación y estados de fallo cerrado; decidir política de red y probar denegación/concesión aislada; y fijar la promoción de cambios vía staging, diff, hash/revisión y transacción del writer único. El usuario no debe elevar A3 ni el comando para hacer que funcione.
