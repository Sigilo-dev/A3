# E6-D1/E6-D2: declarative node packages

Implements the project-scoped node type builder for A3-041 and A3-042. The builder creates versioned JSON packages under `.a3/node-packages/`, with names derived from the namespaced package ID and exact version. Each package declares its node types, collections and exact contribution list. The editor captures typed fields and defaults, input/output ports and multiplicity, basic visual style, and declarative field/port mappings for named import/export formats. It previews the node and a sample instance before saving or exporting JSON.

The host validates the package schema and its internal references before writing it through the existing journaled project store. E6-D2 adds a separate project lock at `.a3/node-packages.lock.json` with exact artifact SHA-256, import origin, declared license/API version, and installed/removed state. Only an entry whose lock metadata and exact artifact hash agree is active. A JSON artifact without a matching install record is available for review, not active. Opening a project reads fixed JSON files from its catalog and never follows package-supplied paths. Invalid, untrusted, or hash-mismatched packages stay untouched, produce diagnostics, and do not register types.

File import passes the selected UTF-8 bytes to the host. The host validates syntax, schema, declarative-only content, supported API version, license declaration syntax, IDs, package/type/collection collisions, and the fixed derived destination before returning a review. The review lists exact IDs, SHA-256, declared license, API version, origin, and destination. The confirmation request must contain the same bytes and digest and explicitly acknowledge the declared license; the host repeats validation and conflict checks before writing. A user-selected filename is display-only and cannot choose the destination. The artifact and lock are staged and journaled together; a failed write is recovered by E1-D1. The hash detects changes/corruption but does not prove who authored the file or grant a license.

Removing a package changes only its lock state; its declarative JSON remains available for reinstall. Entities, resource references, properties, port IDs, and relations are not rewritten. With the type absent, normal canvas fallback retains stored values and endpoints. Reinstall checks the retained artifact against its lock hash and registers the same version again. A changed artifact or a duplicate `(packageId, version)` is never overwritten. Different versions may be installed side-by-side; the existing exact versions and instances are not migrated or silently updated.

Saving these definitions, installing/removing their inert registry data, and importing files use the host's effective `document.edit` capability because this operation writes project metadata. The broader `package.install` capability remains unavailable under E0-C2 and is not granted by this feature. Imported package permissions must be empty. Unknown or absent node types continue through the generic canvas fallback, which keeps the entity's stored properties and ports and leaves relation endpoints intact. This relies on instance records persisting their port IDs; the package definition is not a replacement for that instance data.

The current builder supports a package containing one node type and one custom collection per form submission. Import is from one JSON file; there is no folder/archive expansion or remote catalog. It does not create custom node instances, define executable renderers, or migrate existing instances to changed schemas. Mapping declarations are descriptive data; they do not activate import/export adapters. License validation checks a bounded declaration shape only and is not legal verification. Adding a type to a built-in C4, UML or IoT semantic catalog is not implemented here; collection membership alone does not grant those semantics.

Validation covers the positive package fixture, invalid IDs/defaults/ports/references, manifest contribution mismatch, permissions/executable-looking properties, immutable type versions, transactional save/import and reopen, malformed import, unsupported API version, path-shaped license metadata, repeated package-version conflict, hash mismatch, denied writes, journal rollback, uninstall/reinstall, and unknown-type fallback preserving entity bytes, properties, ports and relation endpoints. The project store uses `document.edit`; no `package.install` grant is needed.
