# E6-D1: declarative node packages

Implements the project-scoped node type builder for A3-041 and A3-042. The builder creates versioned JSON packages under `.a3/node-packages/`, with names derived from the namespaced package ID and exact version. Each package declares its node types, collections and exact contribution list. The editor captures typed fields and defaults, input/output ports and multiplicity, basic visual style, and declarative field/port mappings for named import/export formats. It previews the node and a sample instance before saving or exporting JSON.

The host validates the package schema and its internal references before writing it through the existing journaled project store. A package version is immutable: an existing package/type version cannot be replaced; a new version needs a new filename. Opening a project reads only fixed JSON files from its catalog. Invalid packages stay untouched, produce diagnostics, and do not register types. A valid package registers its type definitions for that project and session; no network lookup, package code loading, script execution, or automatic installation occurs.

Saving these definitions uses the host's effective `document.edit` capability because this operation writes inert project metadata. The broader `package.install` capability remains unavailable under E0-C2 and is not granted by this feature. Imported package permissions must be empty. Unknown or absent node types continue through the generic canvas fallback, which keeps the entity's stored properties and ports and leaves relation endpoints intact. This relies on instance records persisting their port IDs; the package definition is not a replacement for that instance data.

The current builder supports a package containing one node type and one custom collection per form submission. It does not install packages from folders or catalogs, record remote origin/integrity, create custom node instances, define executable renderers, or migrate existing instances to changed schemas. Mapping declarations are descriptive data; they do not activate import/export adapters. Package license is recorded as declared and is not legal verification. Adding a type to a built-in C4, UML or IoT semantic catalog is not implemented here; collection membership alone does not grant those semantics.

Validation covers the positive package fixture, invalid IDs/defaults/ports/references, manifest contribution mismatch, permissions/executable-looking properties, immutable type versions, transaction save and reopen, denied writes, and unknown-type fallback preserving ports and relation endpoints. The project store uses `document.edit`; no `package.install` grant is needed.
