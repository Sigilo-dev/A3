# E3-G2 · conversión segura de imágenes

Implementa A3-039 y las secciones 14.5/23.1–23.2 sobre el contrato Resource E0-A y el escritor/journal E1. La fuente es un Resource local existente, interno o montado con lectura concedida. El conversor inspecciona la firma y metadata de sus bytes; no deduce formato real de la extensión ni del MIME del descriptor. Un `.bin` o un descriptor JPEG que contiene PNG se identifica como PNG. SVG, HTML, PDF de entrada y URLs remotas no se decodifican ni descargan.

## Motor, artefactos y licencias

Se mantiene el candidato de E0-D3: `sharp 0.35.5`, `@img/sharp-win32-x64 0.35.5`, libvips `8.18.7`. PDF usa `pdf-lib 1.17.1`, separado de Sharp, que no anuncia PDF en esta build. Las dependencias e integridades npm están fijadas en el lockfile raíz. `apps/desktop/resources/image/toolchain.lock.json` registra las versiones, integridades y SHA-256 del addon y sus dos DLL. `npm run verify:images --workspace @a3/desktop` contrasta esos archivos antes de desarrollar/compilar. El worker además comprueba versión, plataforma y disponibilidad de los perfiles. Una build ausente o distinta se presenta como componente no disponible. La matriz activa está limitada a Windows x64; Linux queda pendiente.

El `build` de package.json hereda explícitamente `electron-builder.yml` para aplicar el empaquetado base, los avisos y `asarUnpack`, además del artefacto PlantUML existente. Las funciones de estilo usadas por la UI se importan desde el subpath puro `@a3/domain/diagram-style`: el renderer evita cargar el kernel/AJV y mantiene la CSP sin `unsafe-eval`. Ambos ajustes están comprobados por el smoke de conversión sobre los archivos del paquete ASAR.

Sharp declara Apache-2.0, el paquete nativo Windows `Apache-2.0 AND LGPL-3.0-or-later`, y pdf-lib MIT. Se incluyen sus textos de licencia, GPLv3/LGPLv3 y los avisos de terceros de `sharp-libvips v1.3.4` en `resources/image/`. El empaquetador copia esos avisos y deja addon/DLL fuera de ASAR para cargar los binarios Node-API. No se copia ningún binario a Git. Fuentes/procedencia: [Sharp 0.35.5](https://github.com/lovell/sharp/tree/v0.35.5), [sharp-libvips v1.3.4 y avisos](https://github.com/lovell/sharp-libvips/tree/v1.3.4), [libvips 8.18.7](https://github.com/libvips/libvips/tree/v8.18.7), [pdf-lib 1.17.1 y licencia](https://github.com/Hopding/pdf-lib/tree/v1.17.1), [instalación Sharp](https://sharp.pixelplumbing.com/install/). La evidencia de ejecución y estos avisos no completan la auditoría de fuentes correspondientes, modificaciones y obligaciones de redistribución pendiente en E0; no se declara un instalador público listo.

## Matriz ejecutada

Se prueban las doce combinaciones del siguiente cuadro con archivos sintéticos fijados en `fixtures/e3/images/` y el worker que utiliza Electron.

| Entrada real, estática | PNG | JPEG (`.jpg`/`.jpeg`) | AVIF (AV1) | PDF |
|---|---|---|---|---|
| PNG RGBA de 8 bits | Sí | Sí, aplana alpha | Sí, alpha conservado | Sí, imagen raster en una página |
| JPEG con EXIF/orientación | Sí | Sí | Sí | Sí, imagen raster en una página |
| AVIF con alpha | Sí | Sí, aplana alpha | Sí | Sí, imagen raster en una página |

La metadata identifica AVIF como HEIF con compresión AV1. PNG codifica sin pérdida los píxeles normalizados; no recupera pérdidas previas de JPEG/AVIF. JPEG y AVIF usan calidad 1–100 y codificación con pérdida. PNG/AVIF permiten conservar alpha o aplanarlo. JPEG y PDF aplanan sobre el fondo elegido. Todas las salidas aplican orientación, normalizan sRGB/8 bits y eliminan metadata EXIF/XMP/IPTC/ICC; los cambios de profundidad, color, proporción, dimensiones y transparencia se informan antes de preparar y en el resultado. No se promete identidad para todos los perfiles ICC/HDR ni fidelidad pixel a pixel entre sistemas.

PDF se construye desde PNG normalizado local: una página A3/A4, vertical/horizontal, margen 0–50 mm y ajuste manteniendo la proporción de la imagen resultante. La página es blanca; no hay vectorización, formularios, HTML, scripts ni includes. Se validan tipo/documento y dimensiones. El PDF multipágina de diagramas continúa en E3-F2; este perfil de imagen es de una página. GIF animado se inspecciona y bloquea con informe de pérdida potencial: esta matriz no conserva animación. WebP/TIFF/GIF de salida y otros perfiles de la visión general no se habilitan en E3-G2.

## Flujo y seguridad

«Convertir imagen…» aparece en la galería y en archivos que ya tienen Resource ID. En la galería se pueden seleccionar hasta 16 imágenes. Cada elemento del lote conserva configuración y resultado propios; se ejecutan como máximo dos trabajos nativos simultáneos (límite configurable en el servicio host). La UI muestra formato real, tamaño de origen, dimensiones, alpha, calidad aplicable, fondo y pérdidas. No inventa un tamaño estimado: después de preparar muestra el tamaño real calculado. El destino inicial es un archivo nuevo en `assets/converted/`; se puede editar su nombre. Nombres Windows ambiguos, traversal, metadatos, aliases de recursos y destinos existentes se rechazan. Para un archivo aún no catalogado se utiliza primero la incorporación existente de A3.

El renderer solo manda IDs y opciones declarativas mediante IPC validado. Los bytes entran por `ProjectService.openResource`, con `project.read` y `mount.read`/binding local cuando corresponde. No se concede `process.run` ni se acepta una ruta ejecutable. Un worker de Node ejecuta exclusivamente el código fijado de Sharp/pdf-lib sobre buffers raster, con cache deshabilitada, entrada/salida de 32 MiB, 40 megapíxeles, lado máximo de salida 16 000 px, timeout Sharp de 20 s y watchdog de 30 s. La UI permanece fuera del procesamiento nativo. Son límites de aplicación y aislamiento de trabajo/hilo; no se afirma un sandbox de SO ni un límite estricto de memoria nativa.

Transiciones: inspeccionar → convertir → staging → preparar escritura → confirmar → creado. Error/conflicto permiten revisar la propuesta; cancelar descarta solo su staging y plan. Una nueva preparación descarta el plan anterior. No hay escritura del original ni sustitución implícita. El resultado temporal se guarda en una carpeta privada generada bajo app-data, fuera de datos portables. El informe permanece en el host hasta registrarse como procedencia del Resource. El escritor prepara los bytes y un Resource nuevo con procedencia namespaced `a3.media.conversion`, verifica revisión/hash del descriptor y bytes fuente y exige `document.edit`; una fuente montada se vuelve a comprobar con la concesión y raíz actuales. Confirmar repite controles de destino, cambios externos y permisos y usa el journal E1. El recurso solo aparece en el catálogo tras confirmar; un nuevo recurso de imagen aparece automáticamente en la galería sin lista paralela. Un PDF se ve en Archivos como Resource, no se clasifica como imagen de galería.

La creación de descriptor y archivo es una operación lógica recuperable de varios archivos, no una transacción atómica del sistema de archivos. Cada salida de un lote se confirma de manera independiente y puede producir éxito o conflicto. Antes de confirmar se prepara de nuevo sobre el estado aceptado del escritor, conservando las precondiciones de fuente y destino, para admitir commits propios de salidas hermanas; los cambios externos siguen bloqueados. «Cancelar» funciona durante inspección, codificación y staging; una confirmación ya iniciada deja terminar al escritor y su journal para no anunciar una cancelación falsa. El cierre de A3 cancela/espera trabajos y limpia sus temporales. Repetir la confirmación del mismo job confirmado no crea otro Resource. Los jobs de conversión no se reanudan después de reiniciar: un cierre abrupto antes de confirmar puede dejar staging local sin registrar; los bytes originales siguen intactos y cualquier confirmación interrumpida corresponde a la recuperación del journal E1.

## Evidencia y límites de aceptación

`npm run build --workspace @a3/desktop` verifica artefactos, tipos y bundle. `npm run test:images --workspace @a3/desktop` ejecuta matriz/metadata/píxeles/alpha/PDF, entrada inválida/truncada/animada, ausencia de motor, timeout, cancelación real de worker, staging, registro/reapertura, destino concurrente, traversal, fuente obsoleta, revocación documental/de mount y cambio de sesión. El fixture animado tiene dos frames distintos; todos los archivos son sintéticos, sin archivos reales del usuario. `npm run test:images:smoke --workspace @a3/desktop` comprueba la UI real, IPC, worker nativo en Electron, pérdidas visibles, tamaño/destino, confirmación y cancelación sin huérfanos.

A3-039 obtiene evidencia para esta matriz y estas opciones. No se verifican todos los archivos de terceros, imágenes gigantes, corte eléctrico real, publicación ni un límite de memoria nativa del SO. «Reemplazar original» sigue siendo una operación posterior recuperable y no forma parte del flujo entregado.

Evidencia registrada en Windows 10 x64 build 19045, Node 24.13.1 y Electron 44.7.2: 9 pruebas de conversión, 19 de regresión de galería/mounts/seguridad y 5 de estilos; smoke Electron con el bundle local y con `app.asar`. La comprobación del paquete usa `npm run pack:win --workspace @a3/desktop` y `npm run test:images:packaged --workspace @a3/desktop`; es un paquete de prueba sin firma ni instalador de publicación.
